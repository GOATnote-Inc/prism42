## 3. End-to-end voice attestation — instructions

### What we want to capture

For one full caller turn, the worker.log should contain:

- `registered worker` (already present — confirms wiring)
- `job_received` or `room.connected` (worker accepted a dispatch)
- `fsm.transition` (intent classified)
- **`guardrails.check`** with `rail=input` (input rail fired)
- **`attacker.probe`** (adversarial probe fired)
- **`adjudicator.rule`** (rule-based audit fired)
- `tts.start` / `session.say` (audio emitted)

If all six fire in one turn with `elapsed_ms` for each ≤ wrapper
timeout (Guardrails 500 ms, Attacker 400 ms, Adjudicator < 1 ms), the
safety stack is attested working at no measurable latency cost on
the audio path.

### Path A (recommended) — LiveKit Cloud Playground

1. Open `https://cloud.livekit.io/` and sign in to the project that
   owns `wss://ai-therapy-v3svfd9o.livekit.cloud`.
2. From the project dashboard, open **Playground** (or **Sandbox**).
3. Join any room (the worker dispatches per-room).
4. Speak a caller-style utterance — e.g., "Hi, my friend collapsed,
   I need an ambulance to 1200 Main Street." Wait for the agent
   reply.

This path uses LiveKit Cloud's built-in attestation harness — no
Vercel involvement.

### Path B — `livekit-cli` from your laptop

```bash
# install once
brew install livekit-cli

# join a room (replace API key + secret with the project's values
# from the LiveKit Cloud dashboard; do NOT commit them anywhere)
livekit-cli join-room \
  --url wss://ai-therapy-v3svfd9o.livekit.cloud \
  --api-key <KEY> --api-secret <SECRET> \
  --room "attest-h100-$(date +%s)" \
  --identity caller-laptop \
  --publish-mic
```

The CLI joins as a room participant publishing mic audio. The
worker dispatches into the room; you speak; transcripts surface in
the CLI log.

### Path C — Mobile

Mobile attestation via Path A: the LiveKit Cloud Playground works
in mobile browsers. Open the same Cloud-Playground URL on your
phone, grant mic permission, join a room, speak.

### Watching the events fire (run in a second terminal)

```bash
ssh prism-mla-h100 'sudo tail -f /tmp/prism42-logs/worker.log' \
  | grep --line-buffered -E '(registered worker|job_received|fsm\.transition|guardrails\.check|attacker\.probe|adjudicator\.rule|tts\.start)'
```

### Caveat: which worker picks up

Both `prism-mla-h100` (mine) and `warm-lavender-narwhal` (parallel
session's H200) are registered to the same LiveKit Cloud project.
Jobs are dispatched round-robin. If the H200 worker picks up, our
H100's worker.log stays silent for that call — try a second call.
With two workers, the H100 picks up roughly 50 % of calls.

For deterministic targeting we'd need `agent_name="prism42-h100"`
on the H100 worker + `agentName: "prism42-h100"` on the dispatch —
two concurrent edits to worker.py and orchestrator.py respectively,
deferred until the parallel-session race settles.
